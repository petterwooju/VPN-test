# Mac workflow and recovery

## Before any network change

- Create a timestamped log and recovery note in the active workspace. Record `networksetup -getdnsservers Wi-Fi`, `route -n get -inet 168.126.63.1`, enabled proxy flags from `scutil --proxy`, and local DNS listeners with `lsof -nP -iUDP:53 -iTCP:53`. Use current Computer Use state for the actual VPN profile and FlClash switches. The VPN list from `scutil --nc list` is supplementary and can be empty when System Settings has profiles.
- On this Mac, select the dedicated `CoreaVPN_TEST` profile by exact display name. The Puma diagnostic sets `puma.coreavpn.net` for both server address and remote ID. The companion files may be in a different location on the second Mac.
- Classify the DNS baseline. `127.0.0.1` refers to a local relay. Identify its listener and relay Terminal first, and confirm the pre-relay baseline before stopping it or making changes. Never use an unverified 223.5.5.5 as another Mac's restore value. Preserve automatic DNS as automatic if that was the starting configuration.
- If an existing trusted relay is healthy, a test can reuse it with permission to decide what to do with it at the end. If a previous Puma relay is stale, stop it from its own Terminal with Control+C and confirm the saved DNS before starting a fresh session. Never kill an arbitrary process on port 53.

## .net connection and cleanup

- When Codex needs FlClash to reach the Internet, follow [offline pilot preparation](offline-pilot.md). Do not request that the user disconnect FlClash first. Keep all model calls, compilation, UI mapping, permission checks and administrator authorization in the online preparation phase. All work after disabling FlClash, including cleanup, must execute locally without further Codex calls.

- Launch the Mac's existing `Puma-DNS.command` from Terminal so it can prompt for sudo. A copy is bundled in `assets/Puma-DNS/` with its required siblings. The bundled version is a verified fallback for the original Mac's Wi-Fi service, interface en0, and manual upstream 223.5.5.5. Check those prerequisites. A different baseline needs a compatible relay that captures and restores that Mac's own manual or automatic settings. Do not change its baseline to make the bundled script start.
- Use local-only mode without LAN arguments. Wait for the readiness message, Wi-Fi DNS 127.0.0.1 and a plausible A answer from `dig @127.0.0.1 puma.coreavpn.net A`. Do not persist historic numeric addresses. For .com and .kr follow default DNS unless current diagnostics or the user require otherwise.
- If requested, temporarily turn off FlClash's TUN and system proxy inside the prepared local offline sequence when Codex depends on it. Otherwise Computer Use can drive these switches. Verify traffic returns to the physical interface and the relevant proxy flags are off before connecting.
- Enable the chosen VPN switch. Use a bounded wait, normally 25 seconds for connection and another 5 for its route. A switch marked connected plus a new confirmed `ipsecN` route supports measurement. If either check fails, log and disconnect the test connection. Never substitute an external tunnel.
- Use the offline pilot or the local app to choose HTTPS or ICMP. For ICMP the runner verifies the tunnel route to `168.126.63.1` and records 20 ping attempts in `ping-results.jsonl`. For HTTPS, use the following procedure. The runner resolves `speed.cloudflare.com` while the VPN is active, checks the route to the chosen public IPv4 address, and passes that address and the tunnel to `scripts/https_speed.py`. The helper binds its HTTPS sockets to that tunnel and records throughput and idle and loaded response times in `https-results.jsonl`. Missing route evidence invalidates the result.
- Use an explicit cleanup sequence even after a failed connection. Disconnect the selected test profile and check its route, restore any temporary profile edit, stop the test relay with Control+C, confirm the saved DNS and restore FlClash through its UI. If automatic recovery fails, apply the known saved DNS with `sudo /usr/sbin/networksetup -setdnsservers Wi-Fi <saved addresses>`, or `Empty` for a previously automatic service. Verify using `-getdnsservers`. Use the correct service name for the Mac. An owned relay's log and local watchdog are useful for diagnosing recovery, but always read the final DNS state explicitly.

## Server calibration and ranking

- A pilot measures Puma once and ends disconnected. A full Mac comparison attempts all 23 catalog hostnames in each round, including the four .com and two .kr servers. For a repeated calibration, keep that catalog order consistent across rounds. Use the same dedicated `CoreaVPN_TEST` profile for each candidate and restore its original endpoints when the run ends.
- Store run ID, network identifier local to that Mac, round, stable candidate order, timestamps, VPN hostname, measurement hostname, actual tunnel, connection time, measurement statistics and any failure stage. Record each completed attempt so interrupted work can resume. Keep earlier ICMP results and HTTPS results under their original methods.
- Compare HTTPS runs on the same physical network and measurement target. For repeated calibration, use each server's five latest attempts and compare the download and upload rates alongside idle and loaded response times. Cloudflare may route different VPN exits to different points of presence.
- Quick ICMP keeps the first tunnel with at least 18/20 replies and mean RTT at or below 100 ms. Quick FAST keeps the first tunnel with at least 50 Mbps verified download throughput. A timeout or incomplete lane in the timed download fails that measurement. Record upload and idle results independently. The full comparison runs both methods sequentially on the same tunnel, restores the prior network and waits for the user to select a server.

## Download diagnostics

- For a retry of specific failures, give `quick-search.py --operation all --hosts` the exact hostnames from the earlier run. Use a fresh run directory and the same physical interface and subnet. The guardian measures each requested tunnel and restores FlClash after the last host.
- The probe warms up to four connections. Each connection that passes warm-up requests 4 MiB during a single shared six-second window. Inspect the warm-up and timed download records separately. For each failure, report the connection number, last request stage, received and expected bytes, and recorded error. For example, a read timeout after a partial response body identifies where the download stalled.
- Preserve the server-level download failure if any participating connection fails to complete its response. Use partial byte counts for diagnosis only. Compare the retry with the earlier run by hostname and record whether the same failure recurred. Older reports may have only an aggregate error.
